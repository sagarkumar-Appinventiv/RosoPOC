# Workflow preferences
- Prefers quick, lightweight, self-contained test artifacts (e.g., a single HTML page) over setting up full infrastructure for ad-hoc testing. Confidence: 0.6
- Prefers explanations that treat a bug fix as a coordinated system change (tracing how a single number ripples through prompts, parsing, and fallbacks) over isolated one-line patches. Confidence: 0.7
- Applies code changes himself (via his own commits, outside the agent session) and then asks the agent to re-check the updated code against previously identified issues — expects review of the actual current state (git/commits/files), not a re-statement of old analysis. Confidence: 0.5
- Evaluates codebases (including ones built by colleagues) against structured spec/checklist documents with an explicit priority order, and expects findings to be reported in that priority order — including explicit "do NOT flag" items for intentional design decisions (e.g., absent auth, deprioritized features). Confidence: 0.7
- Treats his latest verbal/checklist context as authoritative over older docs/specs, and distinguishes unresolved spec questions (flagged to confirm with the lead/colleagues) from genuine code gaps — expects the agent not to assume answers for open spec items. Confidence: 0.6
- Does not want design/config parameters degraded or lowered just to fit temporary free-tier/API-budget limits during a POC — treats free-tier constraints as throwaway, since production will use paid keys anyway, so the real implementation should not be bent around them. Confidence: 0.7
- Wants bug fixes kept scoped and regression-safe — explicitly asks that a fix not break other working features, preferring minimal, targeted changes over broad rewrites. Confidence: 0.7
- Gets impatient with slow turnaround and truncates deliberation — once a direction is voiced, expects the agent to act immediately rather than stall for more discussion ("do it fast", and "as this is a POC, continue" to end a design back-and-forth and get implementation moving). Confidence: 0.7
- When he pushes back on a change and wants to reconsider the approach, he expects the agent to immediately revert/undo the change (restore the original code) rather than defend it or keep tweaking it — "undo what you changed, fast." Confidence: 0.5
- Considers a POC a sufficient reason to keep scope lean — he cuts off further design debate on a POC and expects implementation to proceed without re-litigating the agreed direction. Confidence: 0.6
- Prefers tight, fixed tolerance windows (e.g., ±10 characters) over loose percentage-based tolerances for content-length/validation checks. Confidence: 0.6
- Prefers a minimum content floor (guardrail) so outputs always contain substantive data; once he understands how it works, he wants that floor enforced visibly and preventively at the frontend (tell the user "below 300 is not allowed" and stop invalid input from being submitted there) rather than handled only as a soft inline hint or silently in the backend. Confidence: 0.6
- Dislikes hidden/opaque logic that silently changes or masks what the user entered (e.g., a backend "effective target" that quietly bumps small values up) — constraints should be transparent and enforced at the source, not kept secret server-side; he questions "why do it secretly?" when logic compensates invisibly. Confidence: 0.7
- Treats the team's production/blueprint architecture as the target his POC pages should converge toward — values its discipline of tagging each content section's provenance (AI-written vs AI+factual vs factual/template), grounding AI text in real data passed in the prompt, and preferring fixed template/factual fallbacks over letting the LLM free-write pure facts (LLM only as last resort for factual content). Confidence: 0.6
- Wants a visible confirmation gate before AI generation runs: on clicking Generate, the exact final prompt (JSON) should pop up full-screen (modal/alert-style) so he can review and confirm "we are going with this final prompt" before anything executes. Confidence: 0.7
- Wants review/confirmation checkpoints before any money-spending or irreversible action executes (e.g., API/billing calls), so the user can inspect the exact payload first — the checkpoint exists to avoid burning paid credits on a wrong input. Confidence: 0.8
- When he says "structure the frontend," he means the design/layout structure — what content and components should go where on the page ("kha kya lage to sahi rahega") — not CSS styling and not file/code organization. Confidence: 0.6
- Directs the POC's focus and effort to the content generation page specifically; doesn't want attention diverted to restructuring other pages (e.g., country/city page redesign) while that page is the priority. Confidence: 0.5
- Delegates implementation decisions to the agent once the overall direction is agreed — "do it whatever u think right" grants the agent latitude over approach and ordering and expects it to proceed, rather than asking for approval on each next step. Confidence: 0.6
- Works from versioned architecture/spec documents checked into the repo (e.g., `rosotravel_batch_architecture_v2.md`) and expects the agent to treat the latest doc as the authoritative implementation blueprint — read it, plan against it, and implement per it, folding in the doc's listed updates and issue-fixes. When he updates the spec himself, he tells the agent which section changed and says "do it", expecting immediate implementation of the updated section. Confidence: 0.7
- Prefers fail-fast behavior on hard, non-retryable API errors (e.g., a 402 credit-limit response): stop immediately with a clear generation error rather than retrying/polling endlessly and flooding logs. Confidence: 0.8
- When a DB schema mismatch surfaces, prefers fixing the schema to match the code (add the intended column via an idempotent migration) over stripping the field out of the code. Confidence: 0.6
- When reviewing a batch of error logs, wants duplicate/repeated occurrences of the same error collapsed and ignored — focus on the root causes rather than fixing each individual duplicate log line. Confidence: 0.7
- Before approving a flow, wants to know whether it will run fully automatically or whether the user keeps a manual option (e.g., "will the system regenerate automatically or will the user have an option?") — he probes the auto-vs-user-control interaction model of a proposed design. Confidence: 0.5
- When reporting a runtime bug, pastes the raw symptom evidence into the chat — backend console logs (e.g., uvicorn INFO request/response lines with status codes), screenshots, or the verbatim rendered UI content of a panel (e.g., a Run Details drawer with all metric values and table cells) — and asks the agent to investigate and trace the root cause ("...check it once") rather than relying only on a prose description of the symptom. Confidence: 0.6
- Prefers card-based layouts over dense tables when comparing multiple models/runs side-by-side — one card per model ("3 models = 3 cards") because it looks more structured and readable. Confidence: 0.7
- Expects in-progress UI state (e.g., a running generation's status/results) to persist across page/tab navigation rather than being wiped when leaving a page — values that a running task stays visible and keeps updating even while the user is on another page. Confidence: 0.7
- Values a planning/consistency phase before batch generation (a "Semantic Consistency Planner") so multi-field content stays coherent, non-repetitive, and semantically consistent across fields — treats a pre-generation plan step as the right architecture rather than generating each field independently. Confidence: 0.6
- Wants a written reference doc for features he builds that catalogs every tunable parameter/"knob" and its exact file/function location, so he can change things himself later ("what parameters kya kuchh hai isme... agar mujhe kuchh change karna ho to i should know") — including a quick "where to change what" mapping table. Confidence: 0.6
